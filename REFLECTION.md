## Project #2: Building With APIs
Question 1 - Defend your research decision. Why did you choose your API provider? Identify an alternative you considered and the evidence from official sources that supported your choice.

Q1 Answer: I chose Open Library because it appeared to be the option that fit my requirements the most. It doesn't require an API key or account, requests that clients cache when possible (developer page), does not assert any new copyright over the data (licensing page), and it is maintained. The only other feasible option was Google Books, but it does not allow building databases locally (Google APIs ToS), which was the exact thing my application required. That alone made Open Library the only real choice for me.

Question 2 - Explain one prototype decision. What design question did your prototype address and why? Describe the alternatives you explored, the decision you made after using it, and where that decision appears in your completed application.

Q2 Answer: I had Claude create two prototypes. One for the UI of the Saved Books page, and one for the privacy logic. The Saved Books UI prototype single-handedly set what my application was going to look like. I wanted to decide on a layout that could be used for the whole app, and I wanted to do so before building anything. It helped me determine that I wanted dark mode colors, a shelf style display of books, and how users will be able to interact with their saved books. The prototype had three options: a shelf grid of cards, a sidebar with a sortable table and status tabs, and a filter rail with a list and a detail panel. The shelf grid looked cleanest and clearest. One decision it helped me decide on was if users could edit the star rating from the Saved Books page or not. Actually seeing the design and amount of room available, I decided to allow rating changes from the Saved Books page, when I previously had decided to have rating changes only on the Book page. Although that UI prototype just showed the Saved Books page, it set what the Search Catalog page and Profile pages would look like too. The rating decision on the Saved Books page's cards is in templates/books/_saved_book_card.html.

Question 3 - Trace your API update. Choose the update performed by your second script. Trace the request from the script through your Django URL, view, and serializer to the stored record and response. In your response, identify which URL pattern routes the request, which view handles it, and which serializer validates the data. Explain how Django identifies the user, how access is restricted, and how you verified that the change was saved.

Q3 Answer: The trace through my second script is as follows. The script contacts my API and sends login data. My API validates the login data and returns a token in response. The script sends a PATCH with the desired change to my API. My API's URL (saved-books/<pk>/) finds the right code and view. Django REST Framework uses the token to figure out who the user is. The view (SavedBookViewSet) then only allows the user to access their own data. My API's serializer (SavedBookSerializer) only formats the JSON response; it does not check input. My API's services.py checks the input of the PATCH and ensures it is valid. If the input data is valid, it is saved to the database. If the input is invalid, services doesn't allow saving to the database. With a successful save, my API will respond by sending an updated save as JSON to the client. The script shows the before and after. Access is restricted by filtering for data whose user equals request.user. Furthermore, without a proper token, the user will only receive a 401 error. I verified the change was saved by manually opening the updated entry in the browser and checking it was changed.

Question 4 - Trace and verify your data. Choose a page that browses saved records. Identify the files and lines of code that implement search, Q objects, filters, sorting, and pagination. Explain what each part does, including which fields are searched, what conditions the Q objects combine, and how the results are filtered, ordered, and divided into pages. Describe one example you checked in the browser and connect the displayed results to the code responsible.

Q4 Answer: The page that browses locally saved data is my Saved Books page (/saved/). The search box and dropdowns are on lines 17-51 of templates/books/saved_books.html. The search function and Q objects are on lines 164-169 of books/services.py, and handles title and author searches. The Q objects are responsible for finding input text in title or author. Filters are on lines 171-187 of books/services.py, and handles filtering data by read status, star rating, and public/private. Sorting is on lines 122-138 and 189-196 of books/services.py, and handles the order in which saved books are displayed in the list. Sorting has four orders: recently saved (the default), title A–Z, first published, and my rating. Pagination is on lines 226-227 and 249-254 of books/views.py, and handles enforcing 12 saved books per page and maintaining filters across list pages. One example I checked in the browser was logging into the demo account "alice", and searching for the word "The" and setting Status to Read. The query returned The Hobbit. The code responsible would be templates/books/saved_books.html:17-51, books/views.py:221, books/services.py:164-169, and books/services.py:171-187.

Question 5 - Push back on the agent. Describe specific bugs or usability problems you found during manual verification. Also describe at least one change you requested and why. Support your answer with screenshots showing before and after (screenshots can be saved in the repo).

Q5 Answer: One bug I found manually was that only the Status filter worked on the Saved Books page. The other filters (rating, visibility, and sort) didn't do anything. Another bug I found during manual testing was the "Clear filters" button on the Saved Books page never appeared while filtering. I told Claude about both of these bugs, Claude fixed them, and I confirmed manually. One thing I requested was to allow users to set ratings on their Saved Books page. I originally decided to have rating be only editable on the Book page. Read status and public visibility would be editable on both the Saved Books page and the Book page. After seeing how clean the UI looked and the stars already on the shelf cards in the prototype, I decided to allow users to edit their ratings on the Saved Books page after all.
